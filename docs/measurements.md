# 実測結果

仕様書 8 章の軽さの目標と、M0（v0.1）の技術検証の結果を記録する。数値は `ci/measure.py` で測り直せる。

## v0.1（2026-10-22）

### 環境

| 項目 | 値 |
|---|---|
| OS | Windows 11 26H2（build 26300） |
| CPU | 12th Gen Intel Core i7-1250U |
| 画面 | 1920x1080、96 DPI（100%） |
| 測定した exe | main の 5c1d3cc を `cargo build --release` したもの |

### 手順

```
cargo build --release
python ci/measure.py
```

仕様書の KB・MB は KiB・MiB（1024 単位）として扱う。起動時間は起動呼び出しの直前から測るので、プロセス生成の時間も含み、遅めに出る。

スクリプトは exe を起動し、パネルが表示されるまでの時間を測る。その後 60 秒待機させ、待機中の CPU 時間、待機後のプライベートメモリとワーキングセットを読む。最後にプロセスを止める。

### 結果

| 項目 | 実測 | 目標（当時の仕様書 8 章） | 判定 |
|---|---|---|---|
| exe サイズ | 206 KiB（211,456 bytes） | 500 KiB 以下（当時の目標。#76 で 1 MiB に見直し） | 達成 |
| 起動時間（起動からパネル表示まで） | 27.5 ms | 100ms 以下 | 達成 |
| プライベートメモリ | 1.60 MiB | 2 MiB 以下 | 達成 |
| ワーキングセット | 11.02 MiB | 5 MiB 以下 | **未達** |
| 待機時 CPU（60 秒間の CPU 時間） | 0.0 ms | 0%（タイマー・ポーリングなし） | 達成 |

### 未達の項目

**ワーキングセット 11.02 MiB（目標 5MB 以下）**

- 原因の見立て: 大半は共有のシステム DLL のページで、EdgePad 自身のデータではない。プライベートメモリは 1.60 MiB に収まっている。トレイアイコン（Shell_NotifyIcon）が shell32.dll と windows.storage.dll を読み込み、この2つだけで読み込みサイズは約16MBある。トレイを入れる前（#3 の時点）のワーキングセットは 8.4MB だった。
- 裏付け: 外から EmptyWorkingSet をかけると、ワーキングセットはほぼ 0 まで下がる。初期化で一度触れただけのページが残っている状態で、常に使われているわけではない。
- 対処の予定: [#10](https://github.com/marby3/EdgePad/issues/10)（v1.0、priority: low）で、初期化の後にワーキングセットを一度縮める方法を試し、待機中の値を測り直す。

## M0 の技術検証: CSP での実機確認

M0 の問いは「フォーカスを奪わないパネルから送ったキーが、ペン描画中の CSP に効くか」だった。答えは「効く」。

- 確認日: 2026-10-22
- 機材: 開発者の手元の、ペンとタッチが使える環境（Windows 11）
- EdgePad: main の 5c1d3cc（v0.1 の内容）

| 操作 | 期待 | 結果 |
|---|---|---|
| 左端の Space を指で押したまま、ペンでキャンバスをドラッグ | 手のひらツールでキャンバスが動く | 効いた |
| 左端の Alt を指で押したまま、ペンでキャンバスをクリック | スポイトで色を拾う | 効いた |
| Alt から指を離す | メニューバーにフォーカスが移らない | 移らなかった |
| Space・Alt から指を離す | キーが戻る（離した後のペンは通常の描画に戻る） | 戻った |

指を離したときにキーアップが1回送られることは、自動テスト（`crates/edgepad/tests/press.rs` の AC1）でも確かめている。

この結果から、WS_EX_NOACTIVATE のパネルと SendInput の組み合わせで、仕様どおりの「指で修飾キー、ペンで描画」が成り立つと判断する。v0.2 以降はこの方式のまま機能を積む。

## v0.2（2026-10-22）

v0.2 の機能（4辺のパネル、設定ファイルと自動再読込、トレイメニュー、ホットキー、ハンドル、ロック・スリープでの解放）がそろった時点で測り直した。

### 環境

v0.1 と同じ機材。測った exe は、main の aa55f78 に [#34](https://github.com/marby3/EdgePad/issues/34) の変更を加え、`cargo build --release` したもの。

### 手順

```
cargo build --release
python ci/measure.py --settings ci/example.ini
```

`ci/example.ini` は仕様書 7 章の設定の例。v0.2 は既定のプロファイルだけを使うので、左に5キーのパネルが1枚出て、ホットキー（Ctrl+Alt+E）も登録される。測定スクリプトは EdgePad を専用の %APPDATA% で起動するので、手元で EdgePad が動いていても測れる。

### 結果

| 項目 | v0.1 | v0.2 | 目標（当時の仕様書 8 章） | 判定 |
|---|---|---|---|---|
| exe サイズ | 206 KiB | 302 KiB | 500 KiB 以下（当時の目標。#76 で 1 MiB に見直し） | 達成 |
| 起動時間 | 27.5 ms | 32.1 ms | 100ms 以下 | 達成 |
| プライベートメモリ | 1.60 MiB | 1.83 MiB | 2 MiB 以下 | 達成（残り 0.17 MiB） |
| ワーキングセット | 11.02 MiB | 12.64 MiB | 5 MiB 以下 | **未達**（#10） |
| 待機時 CPU（60 秒間の CPU 時間） | 0.0 ms | 0.0 ms | 0% | 達成 |

- 設定ファイルなし（固定の5キー）で測ると、プライベートメモリは 1.81〜1.90 MiB だった。設定の有無より、測るたびの揺れのほうが大きい。
- 待機時 CPU は、5回測って3回が 0.0 ms、2回が 15.6 ms と 62.5 ms だった。15.6 ms は Windows のスケジューラの1刻みで、60 秒の間に1〜4回起こされたことになる。続けて測ると 0.0 ms に戻るので、システム全体への通知のような、たまたまの起床と見ている。タイマーやポーリングは使っていない。
- プライベートメモリは、CI の検査（`ci/test_measure.py`）で毎回測り、2 MiB を超えたら落とす。CI では待機 5 秒で測り、測った値を CI のログに出す（「private memory: … bytes」）。手元の待機 5 秒では 1.93 MiB（2,019,328 bytes）で、目標まで 76 KiB しかない。
- （#83 で追記）設定画面を入れた後、手元の待機 5 秒で 2.00〜2.06 MB を測った。同じ日に main のビルドも 2.00〜2.05 MB で、揺れの幅が目標を越えるため、目標と CI の上限を 2.5 MiB に見直した。
- `--settings` を渡すと、設定ファイルのホットキーが登録されたかも報告する。設定が読めずに固定の5キーへ戻ると、ホットキーがないので分かる。ほかのアプリがそのホットキーを先に持っていると「taken by another app」と出て、その時は設定が読めたかを確かめられない。

## v0.6 設定画面の作り直し（2026-10-26、#86）

設定画面を OS 標準の部品（comctl32 v6）とサイドバーで作り直した時点で、設定画面を開いている間と閉じた後のプライベートメモリを測った。

### 環境と手順

v0.1 と同じ機材（画面は 3440x1440、96 DPI）。OS はダークモード。

```
cargo build --release
python ci/measure.py --settings ci/example.ini --settings-window
```

`--settings-window` は、待機の後にトレイメニューから「設定…」を選んで設定画面を開き、前面に出して 1.5 秒待ってからプライベートメモリを読み、閉じて 1.5 秒待ってもう一度読む。これを 5 回繰り返す。起動時に comctl32 v6 が読み込まれていないことも確かめる。CI でも `ci/test_measure.py` が毎回これを測る。

### 結果

| 項目 | #86 の前（main の 6b8eafe） | #86 | 目標（仕様書 8 章） |
|---|---|---|---|
| exe サイズ | 422 KiB | 402 KiB | 1 MiB 以下 |
| プライベートメモリ（一度も開いていない時） | 1.91〜1.96 MiB | 1.91〜1.95 MiB | 2.5 MiB 以下 |
| プライベートメモリ（開いている間、5 回の最大） | 3.04〜3.29 MiB | 3.08〜3.48 MiB | 8 MiB 以下 |
| プライベートメモリ（閉じた後） | 3.04〜3.29 MiB | 3.08〜3.48 MiB | 4 MiB 以下 |
| 開閉 5 回での増え方 | 0.03 MiB 以内 | 0.01 MiB 以内 | 増えない |

- 範囲は 3〜4 回測った値。開閉 5 回の中では値がほとんど動かず、測るたびの揺れ（約 0.3 MiB）のほうが大きい。
- 増えた分の大半は、設定画面ではなくトレイメニューで生じる。メニューを開くと、Windows が文字入力の部品（IME、Text Input Framework）を読み込み、1.95 MiB から 2.9〜3.3 MiB になる。いつ読み込み終わるかで値が揺れる。
- #86 で増えたのは comctl32 v6 と、ダークモードのボタンのテーマ（DarkMode_Explorer）の分で、合わせて 0.1〜0.2 MiB。ライトモードでは、ボタンに既定のテーマを使い、テーマの分を足さない。
- Issue では閉じた後の上限を 3 MiB としていたが、#86 の前の画面でも 3.04〜3.29 MiB で超えていたため、4 MiB とした。

## v0.6 設定画面を別のプロセスに（2026-10-26、#90）

設定画面を同じ exe の2つ目のプロセスで開き、常駐側の IME を止めた時点で測り直した。機材と手順は #86 と同じ（`python ci/measure.py --settings ci/example.ini --settings-window`）。

| 項目 | #86 | #90 | 目標（仕様書 8 章） |
|---|---|---|---|
| 常駐側のプライベートメモリ（起動直後） | 1.91〜1.95 MiB | 1.93 MiB | 2.5 MiB 以下 |
| 常駐側のプライベートメモリ（トレイメニューと設定画面の開閉 5 回の後） | 3.08〜3.48 MiB | 2.32 MiB | 3 MiB 以下、増えない |
| 設定画面のプロセスのプライベートメモリ（開いている間） | （常駐側に含む） | 2.95 MiB | 8 MiB 以下 |
| 常駐側の comctl32 v6 | 開いた後は残る | 読み込まない | 読み込まない |

- 常駐側に残っていた約 1.2 MiB は文字入力の部品で、IME を止めると、トレイメニューを開いても読み込まれない。残りの 0.4 MiB ほどは、トレイメニューを開いたことによる。
- 設定画面のプロセスは、閉じるとプロセスごと終わるので、読み込んだものはすべて返る。

## v0.7（2026-10-28、#119）

v0.7 の機能（辺の共通設定、自由配列と KLE、レイヤーキー、設定画面のサイドバーの作り直し、キー配置とキーマッピングの画面、パイの扇の図、JIS のタブ）をすべて入れた時点で測った。

### 環境と手順

v0.6（#86）と同じ機材（Windows 11 26H2 build 26300、i7-1250U）で、画面は 3440x1440・96 DPI、OS はダークモード。測った exe は、v0.7 の最後の変更（#118）を入れた main の 58e763b を `cargo build --release` したもの。

```
cargo build --release
python ci/measure.py --settings ci/example.ini --settings-window
```

既定の待機 60 秒で 1 回測り、揺れを見るため待機 10 秒（`--idle 10`）でも 3 回測った。exe の隣に別の設定ファイル（テストが残した `target/release/edgepad.ini`）があると、そちらが読まれるため、測る間だけ退けた。

### 結果

前と比べやすいよう、設定画面を別のプロセスにした #90 の値も並べる（#86 の時は設定画面が常駐側と同じプロセスだった）。

| 項目 | v0.6（#86） | v0.6（#90） | v0.7（待機 60 秒） | v0.7（待機 10 秒、3 回の範囲） | 目標（仕様書 8 章） | 判定 |
|---|---|---|---|---|---|---|
| exe サイズ | 402 KiB | — | 716 KiB | 716 KiB | 1 MiB 以下 | 達成（残り 308 KiB） |
| 常駐側のプライベートメモリ（一度も開いていない時） | 1.91〜1.95 MiB | — | 1.84 MiB | 1.98〜2.00 MiB | 2.5 MiB 以下 | 達成 |
| 常駐側のプライベートメモリ（閉じた後） | 3.08〜3.48 MiB（同じプロセス） | 2.32 MiB | 1.96 MiB | 2.02〜2.42 MiB | 3 MiB 以下 | 達成 |
| 設定画面のプロセス（開いている間、5 回の最大） | （常駐側に含む） | 2.95 MiB | 3.78 MiB | 3.76〜3.83 MiB | 8 MiB 以下 | 達成 |
| 開閉 5 回での増え方 | 0.01 MiB 以内 | — | 0.00 MiB | 0.00 MiB | 増えない（64KB 以内の揺れは除く） | 達成 |

- 未達の項目はないので、新しい Issue は作らない。目標の外にあるワーキングセット（12.4 MiB、目標 5MB）は、v0.1 からの既知の未達で [#10](https://github.com/marby3/EdgePad/issues/10) が受け持つ。
- 設定画面のプロセスは #90 から 0.8 MiB ほど増えた。v0.7 で増えた画面の部品（キーマッピングのキーボードの絵のボタンなど）を、開いた時にまとめて作るため。目標の 8 MiB までは十分ある。
- exe は v0.6 から 314 KiB 増えた。大半は設定画面の部品（キー配置・キーマッピング・アプリ別の画面、扇の図）で、1 MiB の目標まで 308 KiB 残っている。v1.0 の出荷ビルドの実測でもう一度見る。
